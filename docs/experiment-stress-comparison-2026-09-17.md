# GAPGUARD 1.0·2.0 안정성 부하 실험 기록

실험일: 2026-09-17
대상: GAPGUARD 1.0 원본과 GAPGUARD 2.0 로컬 코드
목적: 큐 포화, 풀러·센더 지연, 네트워크 장애 상황에서 윈도우 보존 여부 비교

## 결론

2.0은 1.0의 큐 포화 시 `drop_oldest` 정책을 대기 방식으로 바꿨다.
동일한 5단계 부하에서 1.0은 1,800개 중 1,388개를 잃었고, 2.0은 1,800개를 모두 보존했다.

| KPI | 1.0 | 2.0 | 변화 |
|---|---:|---:|---:|
| 윈도우 보존률 | 22.9% (412/1,800) | 100% (1,800/1,800) | +77.1%p |
| 윈도우 유실률 | 77.1% (1,388개) | 0% (0개) | 1,388개 감소 |
| 네트워크 장애 후 복구 | 보존된 데이터만 복구 | 200/200 복구 | 100% 달성 |
| 중복·순서 오류 | 별도 동일 부하 수치 없음 | 0건 | 2.0 통과 |
| 테스트 후 Outbox 잔여 | 0개 | 0개 | 동일 |

### 안정성 관찰값

- 1.0은 큐 포화 시 오래된 윈도우를 삭제했다.
- 2.0은 큐가 가득 차면 컬렉터가 대기했다.
- 2.0의 최대 RAM 큐는 설정값인 30개 또는 5개를 넘지 않았다.
- 2.0 센더 압박 단계에서 SQLite Outbox는 최대 479개까지 증가한 뒤 0개로 배출됐다.
- 2.0 네트워크 복구 단계에서 SQLite 무결성 검사는 정상으로 확인됐다.

## 성능 참고값

성능은 안정성의 보조 지표로 기록한다.

| 지표 | 1.0 | 2.0 | 변화 |
|---|---:|---:|---:|
| 정상 합성 부하 처리량 | 약 781 rows/s | 약 794 rows/s | 유사 |
| SQLite 단건 저장 | 약 10,030 rows/s | 약 9,826 rows/s | 약 2% 감소 |
| 메시지 생성·처리 평균 | 0.012ms | 0.019ms | 약 58% 지연 증가 |

2.0의 강한 부하 단계에서 p99 전송 지연은 최대 약 5.8초였다. 이 지연은 큐와 SQLite에 데이터를 보존하기 위해 컬렉터가 대기한 결과다. 1.0의 고부하 처리량이 높게 보이는 구간은 윈도우를 삭제했기 때문에 직접 비교할 때 주의한다.

## 실험 방법

실제 센서·라즈베리파이·네트워크 대신 합성 컬렉터와 지연을 주입한 SQLite·센더를 사용했다.

- 원본 1.0: 원본의 `drop_oldest` 큐 정책 사용
- 2.0: bounded queue + backpressure 정책 사용
- 각 단계의 완료 윈도우 수, SQLite 보존 수, 전송 수, Outbox 깊이, 지연시간 기록
- 원본 저장소 파일은 수정하지 않음
